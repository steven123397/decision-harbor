# docs/ 文档子树规则

本文件约束 `docs/` 下正式文档的角色、更新方式与交接边界。根目录 `AGENTS.md` 仍是全局协作规则；此处只补充文档体系特有约定。

## 角色划分

| 目录/文件 | 角色 | 写入时机 |
| --- | --- | --- |
| `background/` | 外部输入与已确认约束；首轮产品需求与技术栈边界 | 需求或约束被确认后；实现不得为迁就代码而改写 |
| `design/` | 产品内生的长期设计：范围、不变量、模块边界、接口与关键决策 | 设计收敛后；实现前应有对应设计或明确「沿用背景即可」的说明 |
| `plan/` | 可执行阶段计划与任务切片 | 开始实现或拆分工作前 |
| `status/` | 当前结论、进展、风险、下一步 | 阶段切换、重大阻塞或交接时更新 |
| `index.md` | 正式文档索引与阅读入口 | 新增/归档正式文档时同步链接 |

## 写作原则

- **不双写**：同一事实只在一个主目录维护权威版本；其他位置用链接引用。
- **不编造**：没有确认的设计、计划和进度不要写成既成事实。
- **索引只导航**：`index.md` 列路径与一句话用途，不复制正文。
- **背景只进不出改义**：`background/` 可补充澄清，但不得为了实现便利重新解释已确认口径。
- **状态保持短**：`status/` 只保留当前有效信息；过期细节删掉或链到 plan 历史。

## 模板位置

各角色目录下的 `README.md` 给出最小模板与命名建议。没有真实内容时不要批量生成专题空文档。

- 领域术语表 `design/CONTEXT.md`：仅在确有需要统一的术语时创建。
- 计划归档 `plan/history_plan.md`：仅在项目采用计划归档时创建。
- 审查台账 `status/code_review_status.md`：仅在需要长期维护审查发现时创建。

## 与数据集的关系

`datasets/sales-analytics-v1/` 不在 `docs/` 内，但是正式事实来源之一：

- 机器可读契约：`datasets/sales-analytics-v1/contract.json`
- 人读说明：`datasets/sales-analytics-v1/README.md`
- 权威 fixture：`datasets/sales-analytics-v1/data/`

文档中引用分析表结构、行数、业务口径时，以契约与背景需求为准，并在 `index.md` 中保持可发现。

## 变更检查

更新正式文档后：

1. 确认 `docs/index.md` 能找到该文档。
2. 确认未把进度写进 `background/` 或根 `AGENTS.md`。
3. 确认 design / plan / status 没有互相粘贴大段正文。
