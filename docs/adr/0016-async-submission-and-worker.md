# POST 只受理不执行：202 受理、422 拒绝，执行移入后台 worker

## 决策

v0.2.0 起 `POST /api/v1/query-runs` 不再同步等待查询完成：治理（策略判定）仍在 API 进程内同步执行，通过后落 `received` 并在同一事务转入 `queued`，立即返回 HTTP 202 与运行标识；策略拒绝同步返回 HTTP 422 并落 `rejected` 终态（不入队）。执行由独立 worker 进程完成：认领 queued 运行（FOR UPDATE SKIP LOCKED，ADR-0015）、以分析只读身份执行用户 SQL、把成功终态与结果快照在同一事务内原子发布。API 进程从此不持分析连接池、不执行任何用户 SQL——「API 或 Web 进程不得通过高权限身份执行用户 SQL」的边界从「约定」升格为「结构不可能」。

轮询由客户端驱动（Web 以 500ms 间隔轮询 GET 单条运行）；本版不引入 SSE/WebSocket。

## 支撑设施（随本决策落地）

- **心跳表 `worker_hearts`**：worker 周期写心跳，容器 healthcheck 查标记新鲜度——worker 无 HTTP 端口，健康 = 进程活着且能到达 platform 库；心跳亦为 #10 的租约续期打底。
- **系统开关表 `system_flags` 与排水开关**：`worker.paused` 标志暂停认领（已在执行的跑完为止），用于迁移前排空队列与测试取得确定性；独立建表而非复用 dataset_markers（ADR-0013 界定其为 seed 幂等标记，不得重载语义）。
- worker 与 API 同镜像不同入口；本地 Compose 以统一 `make up` 拉起全部组件。

## 与 ADR-0008 的关系（重开）

ADR-0008 的三个前提在 v0.2.0 委托下全部失效：委托要求「提交请求只负责同步治理和创建运行，后台执行组件异步完成查询」；崩溃恢复要求 API 请求与执行解耦；取消/重试要求可观察的中间态（received/queued/running）。同步等待请求返回呈现「执行中」的做法也让位于轮询呈现。0008 保留原文并标注被取代。

ADR-0009「业务结果一律 HTTP 200」的全面重写（读 200、转移冲突 409、拒绝 422）落在工单 #9；本 ADR 先行固定 202/422 两个提交侧状态码。

## 状态码合同（提交与结果侧）

- 202：受理成功，响应含运行记录（state=queued）。
- 422：策略拒绝，响应含 rejected 运行记录（拒绝码与说明）。
- 409：GET result 在运行未终态（QY_RESULT_NOT_READY）或无可读快照（QY_RESULT_NOT_AVAILABLE，rejected/failed/cancelled）时返回。
- 404 语义不变（记录不存在，含非整数路径 id）。

> 结果读取侧的完整状态码族以 ADR-0018 的端点合同为准（409 未就绪/
> 不可读，及 #14 落地的 410 过期）；本节 409 条款是其在工单 #8 期
> 写下的子集。

## 被否方案

- API 进程内置后台线程执行：崩溃恢复与多实例协同要求执行者可独立重启、可多副本，线程模型把执行生命周期绑死在 API 进程上。
- 受理与入队分两个事务：进程在两步之间崩溃会留下永远停在 received 的孤儿行；同事务落定消除该窗口。
