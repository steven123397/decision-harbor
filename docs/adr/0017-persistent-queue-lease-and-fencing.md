# 持久队列 = platform 库运行表；执行租约与 generation fencing

## 决策

多执行者协同不引入外部 broker：`query_runs` 表即队列（ADR-0015 的字段
设计在此闭环），所有权 = `worker_id` + `lease_expires_at`，接管与发布都
以 `generation` 为前提。

- **认领**：`FOR UPDATE SKIP LOCKED` 选最早的可执行行——queued，或
  running 且租约已过期（接管）。认领写租约并递增 generation；接管
  另递增 attempt（CONTEXT.md「尝试」：接管后的重新执行同样计数；
  attempt 硬上界与自动重试资格在 #11 落地）。
- **续期**：执行期间由守护线程按 `min(心跳周期, 租约/3)` 续期，条件
  UPDATE 要求 worker + generation + running 三者同时成立。续期被拒
  即停止续期；其结果发布由 fencing 兜底拒绝。
- **接管**：只看租约到期，不看心跳存活。租约到期前其余执行者不可
  夺走未过期的运行；到期后任何执行者（含同 ID 重启的进程——本版
  worker 串行执行，自接管不与自身在执行的运行竞态）可重认领。
- **fencing**：终态发布（成功与失败）携带 generation 做 CAS
  （ADR-0016 已定）；本决策补全接管路径——失去所有权的旧执行者
  既不能发布终态，也不能覆盖新执行者的 worker_id / generation /
  状态，被拒绝的成功发布不留快照。

## 理由

- 运行状态、队列与快照同库：受理入队（ADR-0016 的同事务原子性）、
  终态发布 + 快照写入都保持单库事务；外部 broker 会引入跨系统
  双写一致性问题，且崩溃恢复需要的新增组件数为零——执行者死亡后
  租约自然过期，其余执行者按同一认领路径接管，PostgreSQL 是唯一
  事实源。
- SKIP LOCKED 认领无需单点协调者：N 个 Worker 并发抽干队列互不
  重复、互不阻塞；本地 Compose 以 2 个 Worker 容器验证。
- 心跳（`worker_hearts`，ADR-0016）与租约分工：心跳证明进程活性
  （healthcheck 用），租约证明运行所有权（接管判定用）。进程活着
  但卡死（执行线程阻塞、续期线程死掉）时心跳可能仍新鲜，租约则
  必然过期——判接管只认租约才不漏这种半死状态。
- 续期必须在执行路径之外：worker 串行执行会阻塞在查询上，租约
  续期放主循环则长查询期间必然过期、被误接管。守护线程 + 单槽
  活动认领引用是为此服务的最小结构。

## 被否方案

- **外部 broker（Redis / RabbitMQ 等）**：受理「落 received + 入队」
  需要跨系统事务，破坏 ADR-0016 的不可分割受理；运维面与故障模式
  扩大，而本规模（2 Worker、全局并发 4）用不上其吞吐。
- **advisory lock**：会话级、崩溃自动释放，但无可观察的所有权记录
  （谁在执行、租约何时到期），无法支撑接管判定与运行审计。
- **靠心跳判接管**：见上——卡死但活着的执行者心跳仍在，运行永远
  不被接管；心跳是健康信号，租约才是所有权事实。
- **接管不递增 generation**：旧执行者恢复后可直接覆盖新执行者的
  状态与结果，正是 fencing 要堵的窗口；generation 必须随每次
  所有权变更单调递增。

## 与其他 ADR / 工单的关系

- ADR-0015 定义生命周期字段（attempt / worker_id / lease_expires_at /
  generation），ADR-0016 定义受理与最小执行链路；本 ADR 固化多执行者
  协同语义与持久队列选型（规格 #6 给出的实现自由，在此记录理由）。
- 全局并发 4 闸门、attempt 硬上界 3 与自动重试分类在 #11；届时
  worker 将并发持有多个认领，自接管需要进程内排除（排除自己正在
  执行的运行），本版串行模型尚不需要。
