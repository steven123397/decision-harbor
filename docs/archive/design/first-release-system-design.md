# 首轮受治理 SQL 查询链路设计

## 范围与背景

本文档将以下固定输入编译为可实现的首轮系统设计：

- [产品需求](../../background/product-requirements.md)
- [技术约束](../../background/technical-constraints.md)
- [销售分析数据集 v1](../../../datasets/sales-analytics-v1/README.md)
- [机器可读数据契约](../../../datasets/sales-analytics-v1/contract.json)
- [数据集 manifest](../../../datasets/sales-analytics-v1/manifest.json)

数据契约、公开 CSV、生成器、校验器和 manifest 仍是产品输入。本设计只规定应用如何消费这些输入，不复制或重新解释表结构、字段语义、行数和业务口径。

首轮系统面向本地、受信任的企业内部使用场景：用户在最小查询工作台提交显式 PostgreSQL SQL；API 先持久化查询运行，再执行 AST 策略检查；只有通过的语句才使用独立分析只读身份访问分析数据库。查询结果即时返回，查询审计事实持久化到平台数据库。

## 目标与非目标

### 目标

- 在仅安装 Git、Docker 和 Docker Compose 的干净 WSL 环境中，通过统一入口完成构建、启动、迁移、固定数据 seed、就绪等待和测试。
- 提供一条从 Web、API、SQL 策略、分析只读执行到平台审计的端到端链路。
- 用 SQLGlot 的 PostgreSQL AST 执行默认拒绝的语句与对象策略，并用数据库只读权限构成独立的第二道边界。
- 为成功、策略拒绝和执行失败提供稳定状态、错误码、查询运行标识和可追踪审计事实。
- 支持多个本地工作树通过不同 Compose 项目名和宿主端口并行运行。

### 非目标

- LLM、自然语言转 SQL、RAG、MCP、A2A、语义层或 AI 辅助。
- 用户注册、应用鉴权、复杂 RBAC、租户隔离或生产公网暴露。
- 异步任务队列、独立查询 worker、查询取消、自动重试或跨进程恢复执行。
- 查询历史列表、结果导出、结果缓存、结果持久化、图表编辑器或完整运营后台。
- 跨数据库 SQL、平台数据库查询、任意 PostgreSQL 函数或扩展对象访问。

## 术语与核心场景

当前规范术语见 [DecisionHarbor 规范术语](../../../CONTEXT.md)。

### 成功查询

用户提交一条允许的只读查询。系统创建查询运行、完成策略判定、使用分析只读身份执行、限制时长和返回行数、持久化成功终态，然后返回列定义、行数据和审计摘要。

### 策略拒绝

用户提交多语句、修改型语句、禁止结构、未授权对象、未允许函数或无法安全识别的 SQL。系统持久化 `rejected` 终态和稳定原因，不建立分析执行事务。

### 执行失败

SQL 已通过策略，但因列或类型语义错误、容量限制、语句超时、数据库不可用或内部异常失败。系统尽最大可能持久化 `failed` 终态；数据库原始错误和堆栈不得直接暴露给用户。

### 重复启动

同一实例重复执行统一启动入口。迁移到当前 head，seed 在数据版本和摘要完全匹配时无操作；任何未知已有数据或摘要冲突都使初始化失败，不自动覆盖固定数据。

## 查询运行状态与不变量

### 状态

| 状态 | 含义 | 允许持久化的关键事实 |
| --- | --- | --- |
| `received` | 查询运行记录已创建，策略尚未形成终态。 | 原始 SQL、创建时间、策略版本、资源配置快照。 |
| `running` | 策略已允许，分析执行即将开始或正在进行。 | `allowed` 判定、引用对象、开始时间。 |
| `succeeded` | 执行完成且终态审计已持久化。 | 返回行数、是否截断、耗时、完成时间。 |
| `rejected` | 策略拒绝，未访问分析数据库执行用户 SQL。 | `rejected` 判定、稳定原因码、引用对象或拒绝位置摘要。 |
| `failed` | 非策略原因导致查询未成功完成。 | 稳定错误码、安全摘要、耗时、完成时间。 |

允许的迁移只有：

```text
received -> rejected
received -> running
received -> failed
running  -> succeeded
running  -> failed
```

`succeeded`、`rejected` 和 `failed` 是不可变终态。状态更新必须带预期前置状态进行条件写入；更新影响行数不是 1 时视为一致性错误。重试创建新的查询运行，不复用原记录。

API 进程启动时，将本实例上次运行遗留的 `received` 或 `running` 记录收敛为 `failed`，错误码为 `execution_interrupted`。首轮只有一个 API 容器，因此不引入租约或心跳；扩展到多 API 实例前必须重新设计恢复所有权。

始终成立的不变量：

- 用户 SQL 只有在审计记录已持久化且策略判定为 `allowed` 后才能进入分析数据库。
- `rejected` 查询不得建立用户 SQL 执行事务。
- 查询执行器不得接收平台数据库连接或引导身份。
- 只有终态审计写入成功后，API 才能向调用方返回查询结果。
- 平台数据库不保存查询结果单元格值；审计行不等于结果缓存。
- 数据库只读权限不能替代 AST 策略，AST 策略也不能替代数据库权限。

## 模块边界

| 模块 | 负责 | 不负责 | 公共接缝 |
| --- | --- | --- | --- |
| 查询工作台 | 收集显式 SQL、展示运行中状态、结果、拒绝或失败。 | 策略判断、SQL 改写、审计持久化。 | HTTP API。 |
| API 路由 | Pydantic 请求/响应校验、统一 envelope、HTTP 状态映射。 | AST 规则和数据库事务细节。 | `QueryRunService`。 |
| `QueryRunService` | 编排审计、策略、容量和执行顺序；维护状态机。 | 解析 AST、直接执行 SQL、直接拼接数据库语句。 | `SqlPolicy`、`QueryExecutor`、`QueryRunRepository`。 |
| `SqlPolicy` | 解析 PostgreSQL SQL、验证单语句、语句形态、对象、函数和类型转换范围。 | 访问数据库、持久化审计、修改用户 SQL。 | 纯输入/输出策略判定。 |
| `QueryExecutor` | 使用分析只读连接、应用事务与资源限制、执行和序列化结果。 | 平台写入、策略放行、迁移或 seed。 | 已允许的 SQL 与资源配置。 |
| `QueryRunRepository` | 使用平台写入连接创建记录和执行条件状态迁移。 | 分析查询和结果持久化。 | 查询运行聚合的创建、迁移和读取。 |
| 就绪探针 | 使用独立的最小权限身份检查迁移、seed 标记和连接只读状态。 | 执行用户 SQL、把维护元数据暴露给查询执行器。 | `/ready` 的布尔结论。 |
| 引导与迁移 | 创建数据库/身份、应用迁移、校验并 seed 固定数据、设置授权。 | 处理在线用户请求。 | Compose 一次性初始化服务。 |

API 进程持有平台写入池、分析查询池，以及不复用连接的就绪探针引擎。依赖注入只把平台池交给 `QueryRunRepository`，只把分析查询池交给 `QueryExecutor`，只把 readiness DSN 交给就绪探针；业务模块不能接受通用连接或任意 DSN，以免身份边界退化为调用约定。

## 端到端数据流

1. Web 向 `POST /api/v1/query-runs` 提交 `{ "sql": "..." }`，立即进入本地运行中视图并禁止重复提交。
2. API 对 JSON 形态进行校验。只要 `sql` 是字符串且请求体未超过 HTTP 上限，就先在平台数据库创建 `received` 记录。
3. `SqlPolicy` 解析并检查 SQL，返回 `allowed` 或带稳定原因的 `rejected`。
4. 拒绝时，服务将记录条件迁移为 `rejected` 并返回，不连接分析数据库执行用户 SQL。
5. 允许时，服务先取得进程内查询容量，再把记录条件迁移为 `running`。
6. `QueryExecutor` 在分析只读连接上开启显式只读事务，设置语句超时，执行原始 SQL，并最多提取结果上限加 1 行。
7. 服务把成功或失败终态写入平台数据库。成功时只持久化行数、截断标志和耗时，不持久化结果单元格。
8. 终态写入成功后，API 返回统一响应。若分析执行成功但终态审计写入失败，不返回结果；遗留状态由启动恢复收敛。

平台与分析数据库之间不使用分布式事务。顺序和「无终态审计则不返回结果」不变量保证故障不会产生无记录的成功响应。

## 双数据库与身份边界

单个 PostgreSQL 18 容器承载两个逻辑数据库：

| 数据库 | 运行时身份 | 允许能力 | 明确禁止 |
| --- | --- | --- | --- |
| `platform` | 平台写入身份 | 读写查询运行和必要的产品元数据。 | 连接 `analytics`、执行分析 SQL。 |
| `analytics` | 分析查询身份 | 读取契约中的 5 张业务表。 | 读取维护 schema 或迁移版本、`INSERT`、`UPDATE`、`DELETE`、DDL、创建临时对象、访问 `platform`。 |
| `analytics` | 分析就绪身份 | 仅读取迁移版本和 seed 标记以服务 `/ready`。 | 读取业务表、执行用户 SQL、写入、DDL、创建临时对象、访问 `platform`。 |

引导身份只注入 Compose 一次性初始化服务，用于创建逻辑数据库、运行两套 Alembic 迁移、seed 和授权。API 与 Web 容器不得包含引导 DSN 或管理员密码。

分析只读身份的数据库约束包括：

- 分析查询与分析就绪身份只允许连接 `analytics` 数据库；平台写入身份只允许连接 `platform`。
- 从两个逻辑数据库撤销 `PUBLIC CONNECT`，再分别显式授予对应运行时身份；从分析数据库撤销 `PUBLIC CREATE` 和 `PUBLIC TEMP`。
- 分析查询身份只对 `analytics` schema 拥有 `USAGE`，且只对契约表拥有 `SELECT`；它不拥有维护 schema 或 `public.alembic_version` 的读取权。
- 分析就绪身份只对维护 schema 与 `public` 拥有读取 seed 标记和迁移版本所需的最小权限，不拥有任何业务表 `SELECT`。它只注入就绪探针，不能传给 `QueryExecutor`。
- 两个分析身份默认事务只读；执行器每次仍显式开启只读事务并 `SET LOCAL statement_timeout`。
- `PUBLIC` 不得拥有业务 schema 创建权限。新对象不通过默认权限自动暴露，迁移必须显式授权。
- 就绪探针使用无池连接、1 秒连接超时和 1,000 ms 语句超时；API 还把完整 readiness 检查限制在单个 1 秒工作线程截止时间内，超时或不可达都返回 `503 service_not_ready`。

首轮 API 进程同时持有三个受限运行时身份，因此模块边界不能抵御整个 API 进程被攻陷；它防止正常调用路径误用凭据。需要进程级隔离时，应把查询执行器和就绪探针拆为独立服务并重新设计合同。

## 查询审计事实

平台数据库中的 `query_runs` 至少包含以下字段及约束：

| 字段 | 语义 |
| --- | --- |
| `id` | `uuid` 主键，由应用生成，创建后不可变。 |
| `raw_sql` | 用户提交的原始 SQL，不做规范化替换。 |
| `status` | 带 `CHECK` 的 `text`：`received`、`running`、`succeeded`、`rejected` 或 `failed`。 |
| `policy_decision` | 带 `CHECK` 的 `text`：`not_evaluated`、`allowed` 或 `rejected`。 |
| `policy_version` | 非空 `text`；策略规则版本、数据集版本和 contract 摘要的稳定组合。 |
| `referenced_objects` | 非空 `jsonb` 数组；元素只能是规范化、去重、排序后的契约业务表，例如 `analytics.orders`。允许的空数组只表示没有解析任何数据库对象的常量表达式。 |
| `statement_timeout_ms`、`max_rows` | 正整数；本次运行实际使用的资源边界快照。 |
| `returned_row_count` | 非负整数；仅成功终态非空，最大为 `max_rows`。 |
| `result_truncated` | `boolean`；仅成功终态非空。 |
| `error_code`、`error_summary` | 最长分别为 64 和 512 字符；拒绝或失败时非空，成功时为空。 |
| `created_at`、`started_at`、`finished_at` | `timestamptz` UTC 时间；`started_at` 仅表示分析执行开始。 |
| `duration_ms` | 非负整数；从创建到终态的生命周期耗时，非终态为空。 |

数据库检查约束必须保证终态字段组合合法，例如 `succeeded` 不得有错误码，`rejected` 必须有 `policy_decision = rejected`，`running` 必须有开始时间和 `allowed` 判定。表以主键支持按 ID 读取，并建立只覆盖 `received`、`running` 的状态/创建时间索引支持启动恢复。原始 SQL 按需求持久化，但应用日志默认不重复输出 SQL；数据库原始错误、堆栈、DSN 和凭据不得进入 `error_summary`。

首轮没有应用身份体系，因此不伪造 `actor_id`。引入鉴权后，通过显式迁移增加真实主体，而不是把所有历史记录标成同一虚构用户。

## SQLGlot AST 策略

`SqlPolicy` 是纯模块：输入原始 SQL 和固定策略配置，输出允许结论或稳定拒绝；它不连接数据库，也不改写 SQL。SQLGlot 版本必须固定，策略行为由单元测试锁定。

检查顺序如下：

1. 检查 SQL UTF-8 字节长度和空白内容；空 SQL 或超过 64 KiB 的 SQL 形成有记录的策略拒绝。
2. 使用 PostgreSQL dialect 解析完整输入。解析失败、空解析结果或解析得到不止一个表达式时拒绝；单个尾随分号可以接受。
3. 根表达式只允许只读查询：`SELECT`、`WITH ... SELECT` 以及 `UNION`、`INTERSECT`、`EXCEPT` 组合。`VALUES`、`EXPLAIN`、`SHOW` 和其他命令根节点不在首轮允许集。
4. 遍历完整 AST，拒绝任何数据修改、DDL、事务、过程调用、`COPY`、`SELECT INTO`、修改型 CTE 和行锁子句。出现未列入首轮支持语法集的节点时默认拒绝，不根据节点看似只读而放行。
5. 按 CTE 作用域解析表引用。物理表只能是 contract 中 5 张表，允许不带 schema 或显式 `analytics.<table>`；数据库限定名、其他 schema、系统目录和 `information_schema` 一律拒绝。
6. CTE 名可以被后续查询引用，但不得与允许的物理表同名，避免对象遮蔽导致审计与执行理解不一致。所有嵌套查询和集合分支都执行相同对象检查。
7. 函数调用采用版本化允许列表。首轮仅允许 `count`、`sum`、`avg`、`min`、`max`、`abs`、`round`、`floor`、`ceil`、`lower`、`upper`、`length`、`trim`、`concat`、`substring`、`date_trunc`、`extract`、`coalesce`、`nullif`、`row_number`、`rank`、`dense_rank`、`lag` 和 `lead`。schema 限定函数、用户定义函数、表函数、未知函数和副作用函数默认拒绝。
8. `CAST` 和 `DataType` 采用内建标量允许集：文本、字符、整数、定点数、布尔、日期、时间戳和带时区时间戳。长度、精度和 scale 只能是有界字面量；数组、未列入的内建类型和表达式型参数默认拒绝。SQLGlot 解析出的 `ObjectIdentifier`、用户定义或 schema 限定类型一律按对象访问拒绝，因此 `regclass`、`regrole`、`regproc`、`regprocedure`、`regoper`、`regoperator`、`regnamespace`、`regtype` 及其他 catalog 解析类型不能通过转换绕过对象策略。
9. 返回规范化、去重并排序的物理对象集合，供审计记录；不把格式化后的 SQL 当作执行输入。任何允许结论中，这个集合只能包含契约业务表。

函数和类型允许列表不是字符串黑名单：函数名与转换目标都必须来自 AST 节点并按 PostgreSQL 语义规范化。`CASE`、`CAST`、算术、比较、布尔和窗口 frame 等非函数表达式按 AST 类型检查。表引用允许集在启动时从固定 `contract.json` 读取，manifest 中的 contract 摘要不匹配时 API 不进入就绪状态，避免手工复制表名造成漂移。

策略允许不引用物理表的常量 `SELECT`，但仍执行函数、类型和禁止节点检查；它不得触发未审计的数据库对象解析。即使 SQLGlot 错判或漏判，分析查询身份和只读事务仍必须阻止数据库写入。

## 资源限制与结果语义

| 配置 | 首轮默认值 | 安全上限 | 行为 |
| --- | --- | --- | --- |
| HTTP 请求体 | 128 KiB | 固定 | 超限在解析前返回 `invalid_request`，无法创建查询运行。 |
| SQL 字节数 | 64 KiB | 64 KiB | 有效 JSON 中的字符串超限后创建 `rejected` 记录。 |
| `QUERY_STATEMENT_TIMEOUT_MS` | 5,000 ms | 30,000 ms | 在分析事务中通过 `SET LOCAL` 应用。 |
| `QUERY_MAX_ROWS` | 500 | 5,000 | 最多向客户端返回该数量的行。 |
| `QUERY_MAX_CONCURRENCY` | 4 | 16 | API 进程内同时执行的分析查询数量。 |
| `QUERY_CAPACITY_WAIT_MS` | 250 ms | 1,000 ms | 等待执行名额的最长时间，超时返回容量错误。 |

配置在 API 启动时校验，越界或无法解析使服务不就绪，不能静默退回无限制值。连接池大小不得超过查询并发上限；平台连接池独立配置，不能被长查询耗尽。

执行器使用服务端游标或等价的有界提取方式读取 `max_rows + 1` 行。出现额外行时只返回前 `max_rows` 行并设置 `truncated = true`；`returned_row_count` 表示实际返回行数，不声称是查询总行数。截断属于成功，但 Web 必须醒目标示，防止用户把局部结果误认成完整结果。

结果列使用 `{ "name": string, "type": string }`，行使用与列位置对应的数组，避免重复列名丢失。`numeric` 和 `bigint` 以十进制字符串返回，日期时间使用 ISO 8601，布尔值、32 位整数、字符串和 null 使用原生 JSON 类型；无法稳定序列化的类型使运行以 `unsupported_result_type` 失败，不使用隐式 `str()` 掩盖语义。

## 最小 API 与错误语义

所有端点使用统一 envelope：

```json
{
  "data": {},
  "error": null
}
```

错误时 `error` 至少包含稳定 `code`、面向用户的 `message`，存在查询运行时还包含 `query_run_id`。`message` 可以改进措辞，客户端分支只能依赖 `code` 和查询运行状态。

| 端点 | 成功语义 | 失败语义 |
| --- | --- | --- |
| `GET /health` | `200`；只证明 API 进程可响应。 | 进程不可响应时由容器健康检查判定失败。 |
| `GET /ready` | `200`；两个数据库可达、迁移为预期 head、seed 标记与 contract/manifest 匹配、分析就绪身份为只读。 | 依赖探测在 1 秒内未完成或失败时返回 `503 service_not_ready`，不泄露凭据或内部 DSN。 |
| `POST /api/v1/query-runs` | 同步执行；`200` 返回终态 `query_run` 和即时 `result`。 | 根据下表返回稳定 HTTP 状态，同时尽可能返回已持久化的查询运行。 |
| `GET /api/v1/query-runs/{id}` | `200` 返回当前状态和审计事实，包括拒绝或失败终态。 | `404 query_run_not_found`。 |

POST 不返回 `202`，也不创建后台任务。查询由 5 秒默认语句超时和进程并发上限约束；Web 在请求未完成时显示运行中状态。GET 可以观察已持久化的 `received` 或 `running`，也可以在 POST 响应丢失后恢复审计事实，但不返回历史结果单元格。

| HTTP 状态 | 稳定错误码 | 查询运行终态 | 语义 |
| --- | --- | --- | --- |
| `422` | `invalid_request` | 无记录 | JSON 缺失、`sql` 不是字符串或请求体在解析前超限。 |
| `422` | `sql_empty`、`sql_too_large`、`sql_parse_error`、`multiple_statements`、`sql_statement_not_allowed`、`sql_object_not_allowed`、`sql_function_not_allowed`、`unsupported_sql` | `rejected` | 可审计的策略拒绝，未执行用户 SQL。 |
| `400` | `query_semantic_error` | `failed` | 数据库发现列、类型或表达式语义错误。 |
| `429` | `query_capacity_exceeded` | `failed` | 未在短暂容量等待窗口内取得执行名额。 |
| `504` | `query_timeout` | `failed` | PostgreSQL 语句超时。 |
| `503` | `analytics_unavailable`、`audit_unavailable`、`service_not_ready` | `failed` 或无记录 | 依赖或审计持久化不可用。 |
| `500` | `policy_internal_error`、`internal_error` | `failed` | 未分类内部错误，响应不暴露底层异常。 |

GET 成功读取一个 `rejected` 或 `failed` 记录时仍返回 HTTP `200`，因为读取操作成功；查询结果通过 `query_run.status`、`error_code` 和 `error_summary` 表达。POST 的错误 envelope 与持久化字段使用同一个错误码映射，避免两套语义漂移。

## 最小查询工作台

首屏就是可用的查询工作台，不建立营销页或运营导航。它包含 SQL 输入区、提交命令、请求状态区、查询运行摘要，以及互斥的结果、拒绝和失败视图。

交互状态如下：

- 初始状态允许编辑和提交；空输入由客户端提示，但服务端仍是最终边界。
- 提交后保留原 SQL，禁用重复提交并展示明确的运行中状态。首轮不提供隐式重试或取消。
- 成功后展示查询运行 ID、状态、返回行数、耗时和截断标志，并用可横向滚动的表格呈现列与行。
- 拒绝视图展示稳定错误码、可读原因和查询运行 ID，不把拒绝描述成系统故障。
- 失败视图区分超时、容量、查询语义和服务不可用；重新执行必须由用户显式触发，并产生新 ID。
- API 返回未知错误码时使用通用失败文案，同时保留错误码和记录 ID 便于追踪。

Web 不复制 SQL 策略，不根据字符串猜测能否执行；客户端校验只改善交互。查询结果只保存在当前页面内存中，刷新后可以按 ID 读取审计事实，但不能恢复结果行。

## 迁移与幂等 seed

平台和分析数据库维护独立 Alembic 迁移链与版本表：

- 平台迁移创建 `query_runs`、`text + CHECK` 状态约束、恢复索引和迁移元数据。
- 分析迁移在 `analytics` 数据库的 `analytics` schema 中创建 contract 的 5 张表、字段、主外键、唯一约束和定点数类型，不添加订单总额等派生业务字段。
- 分析数据库另有只对引导身份开放写入的维护 schema，用于 seed 标记；分析就绪身份可读取该标记，分析查询身份和用户 SQL 都不能访问该 schema。
- 每次迁移显式重建最小授权，不能依赖宽泛默认权限。集成测试将数据库实际 schema 与 `contract.json` 逐字段比较。

seed 流程必须先运行数据集 `validate.py`，再执行以下单事务步骤：

1. 获取以数据集名为键的 PostgreSQL advisory lock，阻止并发 seed。
2. 计算并核对 manifest、contract、生成器和各 CSV 的 SHA-256 与预期行数。
3. 若维护 schema 中存在完全相同的数据集版本、contract 摘要和 manifest 摘要，并且 5 张表行数均匹配，则无操作成功。
4. 若没有 seed 标记且 5 张目标表全空，按外键依赖顺序使用 `COPY` 载入 CSV，保留 contract 中的显式 ID，并同步相应序列。
5. 在提交前核对表行数、订单状态分布、日期范围、外键和 contract 业务约束；随后写入 seed 标记并一次提交。
6. 若已有业务行但没有匹配标记，或版本、摘要、行数任一冲突，则以 `seed_conflict` 失败并回滚，不执行 `TRUNCATE`、覆盖或猜测性修复。

该策略让重复 seed 可证明为无操作，并让失败载入完整回滚。未来数据集升级必须有独立迁移设计；首轮不把「删除 volume 重来」伪装成线上迁移方案。本地确需清空数据时只能通过明确的破坏性清理命令删除当前 Compose 项目的命名卷。

## Compose 运行与并行隔离

仓库提供不依赖宿主 Node.js 或 Python 的 Bash 入口，至少公开 `./dev up`、`./dev test` 和 `./dev down`：

- `./dev up` 构建镜像，启动 PostgreSQL，运行一次性引导/迁移/seed 服务，随后启动 API 和 Web 并等待 `/ready` 与 Web 健康检查。
- `./dev test` 在 Compose 服务内运行 pytest、Vitest 和 Playwright 所需验证。
- `./dev down` 停止当前实例但保留数据卷；任何删除卷的命令必须使用不同、显式的破坏性名称。

Compose 必须满足：

- 项目名由 `COMPOSE_PROJECT_NAME` 配置；入口可以从当前工作树路径生成默认值，但必须允许显式覆盖。
- `WEB_HOST_PORT`、`API_HOST_PORT` 和宿主绑定地址可配置，默认只绑定 `127.0.0.1`。数据库不映射宿主端口。
- 不设置 `container_name`，不为网络或数据卷设置全局 `name`，不挂载跨工作树共享的绑定目录。
- 每个实例的容器、默认网络、PostgreSQL 卷和测试产物都由 Compose 项目名命名。
- API 通过 Compose 服务名访问 PostgreSQL；浏览器通过 Web 同源代理访问 API，避免把容器内部地址暴露到前端配置。
- API/Web 运行时环境只含各自所需的非管理配置；引导凭据只存在于一次性初始化服务。

默认回环绑定和无应用鉴权是配套决定：首轮只面向本地受信任环境。将绑定地址改为非回环不代表系统具备生产安全性；任何共享网络部署都必须先引入鉴权、主体审计、传输安全和部署边界设计。

## 关键决策与理由

### 同步执行，不引入异步 worker

首轮查询受 5 秒默认超时和并发上限约束，同步 POST 能提供最小可运行链路，并避免新增队列、任务租约、结果存储和 worker 恢复协议。被放弃的方案是 `202 +` 后台轮询；当查询时长需要超过 HTTP 边界、必须支持取消或需要横向扩展时重新评估。

### 结果即时返回，不持久化结果行

需求要求持久化审计事实，没有要求保存结果数据。只返回结果可以避免在平台数据库复制业务数据、扩大敏感面和引入结果生命周期。代价是 GET 和页面刷新不能恢复结果；若未来需要历史结果或导出，必须单独设计授权、保留期、容量和删除语义。

### AST 默认拒绝，并叠加数据库只读权限

只使用字符串黑名单容易被注释、嵌套结构和语法变体绕过；只使用数据库只读权限又不能限制系统目录、未授权对象和资源滥用。因此策略基于完整 AST、对象范围、函数与类型允许列表，数据库角色与只读事务负责独立兜底。显式验证类型可避免 PostgreSQL 对象标识转换在没有 `Table` 节点时解析 relation、role、function、namespace 或 type catalog。函数或类型允许集会限制部分合法 PostgreSQL 分析能力，但这是首轮可解释安全边界；扩展能力必须带 AST 与真实数据库测试。

### 先持久化审计，再执行用户 SQL

平台和分析是两个逻辑数据库，无法使用单个本地事务。先创建审计记录并在终态写入前不返回结果，能保证每次实际执行都有可追踪记录。被放弃的方案是执行成功后再补记审计，因为进程中断会产生无记录执行。

### seed 冲突时失败，不自动覆盖

固定 CSV 是权威数据，未知已有行不能被当作同一版本。manifest 匹配的无操作与冲突失败能证明幂等性，并避免自动 `TRUNCATE` 掩盖漂移。未来确需数据版本升级时用显式迁移设计替代通用覆盖逻辑。

### 首轮无应用鉴权，默认只允许本机访问

背景明确排除用户注册和复杂 RBAC，且交付环境是本地 WSL。首轮不伪造用户体系，Web/API 宿主端口默认绑定回环地址。该决定不能外推到共享或生产部署；部署边界改变即触发鉴权与主体审计设计。

## 失败处理与迁移

- 平台审计创建失败时不执行用户 SQL，返回 `audit_unavailable` 且没有查询运行 ID。
- 分析执行成功但终态审计写入失败时丢弃响应结果，返回 `audit_unavailable`；启动恢复把遗留记录标记为 `execution_interrupted`。
- 分析连接在异常、取消或超时后必须回滚并归还或丢弃，不能带着会话级状态进入连接池。
- 错误映射以 SQLSTATE 类别和已知驱动异常为输入，未知异常统一映射为 `internal_error`；外部响应不包含原始数据库消息。
- `/ready` 失败不影响 `/health` 的进程存活语义；数据库完全不可达或探针卡住时也必须在 1 秒截止时间内返回 `service_not_ready`，Web 应阻止提交并展示服务未就绪。
- Alembic 迁移失败或 seed 冲突使初始化服务非零退出，API/Web 不启动。重复 `./dev up` 从当前迁移状态继续，不跳过失败检查。
- 迁移回滚只处理应用 schema；固定数据集版本替换、身份模型变更和跨数据库拆分都需要新的设计，不在通用 downgrade 中猜测恢复。

## 测试接缝与验证原则

### 单元测试

- `SqlPolicy` 作为纯模块覆盖允许的 SELECT、CTE、连接、子查询、聚合、窗口和集合操作，以及多语句、所有禁止语句、修改型 CTE、`SELECT INTO`、锁、CTE 遮蔽、系统对象、schema 限定、函数与安全类型允许列表、对象标识类型转换和未知节点默认拒绝。
- 状态机覆盖全部允许迁移、终态不可变、条件写入冲突和启动恢复。
- API 错误映射覆盖每个稳定错误码、HTTP 状态和脱敏规则，`/ready` 覆盖阻塞依赖的截止时间。
- 结果序列化覆盖重复列名、null、定点数、bigint、日期时间、截断和不支持类型。
- Web 使用 Vitest 覆盖初始、运行中、成功、拒绝、失败、截断、全部已知错误码和未知错误码视图；测试通过与真实 API 相同的客户端边界驱动组件。

### PostgreSQL 集成测试

必须使用真实 PostgreSQL 18，而不是内存数据库：

- 在空数据库上运行两套迁移与 seed 两次，证明第二次无操作且 contract、manifest、行数、状态分布和日期范围保持一致。
- 将实际表、列、类型、可空性、主外键和唯一约束与 `contract.json` 比较。
- 证明平台写入身份可以写审计但不能连接分析数据库；分析查询身份可以 SELECT 契约表，但不能读取维护元数据、写入、创建对象、访问平台数据库或绕过只读事务；分析就绪身份只可读取迁移版本和 seed 标记。
- 经真实 API 验证成功、安全转换、对象标识类型策略拒绝、数据库语义失败、超时、容量拒绝、截断、审计终态和启动恢复。
- 证明拒绝查询未到达分析执行接缝，成功结果行没有写入平台数据库。
- 使用两个 Compose 项目名、两组宿主端口同时启动实例，证明容器、网络、卷和数据互不共享。

### 浏览器测试

Playwright 在完整 Compose 环境覆盖：

- 提交允许查询，观察运行中状态、结果表、行数、耗时和查询运行 ID。
- 提交策略禁止查询，看到拒绝原因且没有结果表。
- 触发可控执行失败或超时，看到与拒绝不同的失败视图。
- 返回超过行上限的查询时，表格只展示上限内行并明确显示截断。
- API 未就绪时不能误报成功；恢复就绪后可再次显式提交。

### 证据边界

- 机械证据：Markdown 链接、OpenAPI schema、迁移 head、数据 contract/manifest 摘要和格式检查。
- 行为证据：单元、真实 PostgreSQL 集成和 Playwright 主流程均通过公共接缝观察行为。
- 共识证据：设计评审确认本文没有改写背景范围、数据口径或非目标。测试通过不能替代这一确认。

## 延后决策

- 应用鉴权、真实主体审计、RBAC、租户隔离和非本机部署安全。
- 异步 worker、查询取消、队列、租约、自动重试和多 API 实例恢复。
- 查询历史列表、结果持久化、缓存、导出、分享与保留策略。
- 函数允许列表之外的 PostgreSQL 能力、扩展、用户定义函数和新分析数据集。
- LLM、自然语言转 SQL、RAG、MCP、A2A、语义层、图表与运营后台。

这些事项没有进入首轮接口或数据模型。只有背景范围改变或已列出的重新评估条件出现时，才新增正式设计。
