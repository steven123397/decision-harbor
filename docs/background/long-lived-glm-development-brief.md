# DecisionHarbor 长期 GLM 分支 v0.2.0 开发委托

本委托只用于 DecisionHarbor 的长期 GLM 分支，不属于 AgentShip v0.2.0 正式候选测试，不参与评分，也不替代 Agentship baseline 目录下的 `development-brief.md`。正式竞赛中的 GLM 5.3 + zcode 仍须从统一冻结 baseline 出发，使用正式委托和相同评测边界；不得复用本长期分支的实现成果。

## 工作方式

继续使用长期 GLM 工作树在执行时的当前提交，不重置到正式竞赛 baseline。开始开发前先检查分支与工作树状态，阅读工作树中生效的 Agent 规则、Skill 体系、文档入口、产品需求和项目状态。该工作树已经完成文档体系重构；保持现有结构，不恢复旧文档目录，也不根据本委托另建平行文档体系。

独立完成本版本设计与实现，不读取、复制或移植 DecisionHarbor 主分支的 v0.2.0 实现代码。可以参考本委托描述的产品合同，但模块边界、状态持久化方式、队列技术、Worker 组织、依赖选择、配置结构、测试分层和文档表达均由你决定。发现产品合同存在实质歧义时再向用户提问；普通实现决策自行完成并记录理由。

按工作树的新文档体系管理本版本知识：规格、工单和实施进度进入 GitHub Issues，不在 `docs/` 下重建旧的 design、plan 或 status 文档；新领域术语确认后更新 `CONTEXT.md`，不可逆设计选择记录为独立 ADR。开始拆解前先读取现有 Issues，尤其是查询运行清理与归档、跨实例容量协调，复用或重开已有问题，不创建含义重复的工单。

本版本会有意重开 ADR-0008「同步运行语义」与 ADR-0009「业务结果返回 HTTP 200」，并扩展 ADR-0011 的截断语义。必须按仓库规则显式记录替代决策及迁移理由，不得静默改写旧 ADR；`CONTEXT.md` 中现有查询生命周期和终态定义也应在新状态模型确认后同步扩展。

## 产品目标

把 v0.1.0 的同步受治理 SQL 查询链路扩展为可恢复的异步查询运行系统：提交请求只负责同步治理和创建运行，后台执行组件异步完成查询，用户通过工作台或 HTTP API 查询状态、读取有限结果、取消运行、重试失败或取消的运行，并查看历史记录。

实现方式可以与主分支完全不同，但以下外部行为和安全结果必须等价。

## 产品合同

### 1. 查询生命周期

- 合法 SQL 提交后立即返回 HTTP 202 和运行标识，不同步等待查询完成。
- 运行至少能够表达 `received`、`queued`、`running`、`succeeded`、`failed`、`cancelling`、`cancelled` 和 `rejected`。
- 策略拒绝同步返回 HTTP 422，保存 `rejected` 运行，但不进入后台执行队列。
- 终态不可逆。同一运行不能同时发布互相矛盾的成功、失败或取消结果。
- 后台执行组件崩溃或失去所有权后，其他实例能够恢复未完成任务；失去所有权的旧执行者不得覆盖新执行者或发布过期结果。
- 系统必须支持 2 个 Worker 实例协同运行，并将用户查询的全局并发限制为 4。一次运行最多自动尝试 3 次。

这里固定的是可观察的一致性与恢复结果，不强制采用 PostgreSQL 队列、租约字段、generation fencing 或主分支的具体状态机实现。若选择其他方案，必须在本地 Compose 环境中提供同等的持久性、接管、防旧执行者发布和全局并发语义。

### 2. 提交与幂等

- `POST /api/v1/query-runs` 接收 SQL 和可选幂等键。
- 相同幂等键重复提交相同 SQL 返回原运行，不创建重复任务。
- 相同幂等键提交不同 SQL 返回稳定冲突错误。
- SQL 大小、AST、函数、类型转换和对象访问范围仍在用户查询进入后台执行前完成治理。

### 3. 查询、取消与重试

- `GET /api/v1/query-runs/{id}` 返回状态、attempt、时间、审计事实和稳定错误摘要。
- `POST /api/v1/query-runs/{id}/cancel` 可幂等调用。排队中的取消确定生效；运行中的取消允许 best effort 中止底层查询，但取消事实在终态发布前获胜时不得再发布结果。
- `POST /api/v1/query-runs/{id}/retry` 只允许重试 `failed` 或 `cancelled` 运行，并创建带 `retry_of` 关系的新运行。
- `rejected` 运行必须修改 SQL 后重新提交；`succeeded` 运行不可重试。
- `GET /api/v1/query-runs` 按创建时间分页返回历史运行。

### 4. 结果快照与保留

- `GET /api/v1/query-runs/{id}/result` 读取已保存结果，不重新执行 SQL。
- 成功终态和结果快照必须作为一个不可分割的发布结果：不能看到成功状态却读不到本应存在的快照。
- 快照最多保存 500 行和 1 MiB，并明确返回行数与 `truncated`。单行自身超过上限时以稳定错误结束运行。
- 结果保留 24 小时，审计运行继续保留。未完成或结果不可用返回 HTTP 409，结果过期返回 HTTP 410。
- 过期清理可重复执行，不得破坏仍在保留期内的结果或运行审计。

### 5. Web 工作台

- 提交后通过轮询展示排队、运行和终态，不依赖 SSE 或 WebSocket 才能完成主流程。
- 用户可以查看成功结果、拒绝或失败原因、取消状态、重试关系和历史记录。
- 对结果未完成、不可用或过期提供清晰反馈。
- 保持桌面和窄视口可用、键盘可操作、状态层级清楚；不要求复刻主分支组件结构或视觉样式。

### 6. 不可退化边界

- 保留 v0.1.0 已建立的 SQL AST 治理、函数与类型允许范围、对象范围、只读分析身份和稳定错误摘要，不得重新引入已修复的治理绕过。
- 保留固定销售数据契约、定点金额语义、双数据库职责隔离、幂等迁移与 seed。
- API 或 Web 进程不得通过高权限身份执行用户 SQL。后台执行组件也只能使用分析只读身份执行用户 SQL。
- 本地环境继续支持一条统一启动路径、真实数据库迁移、健康与就绪检查，以及多个工作树通过独立项目名、端口、网络和数据卷并行运行。
- 本版本不扩展 LLM、自然语言转 SQL、RAG、MCP、A2A、认证、租户/RBAC、图表、保存查询、批处理、优先级、定时任务或多区域高可用。

## 实现自由

在满足上述产品合同和不可退化边界的前提下，可以：

- 重构或替换 v0.1.0 内部模块；
- 自主选择持久队列、并发协调和恢复机制；
- 调整数据库模型、进程数量、内部 API、错误码名称和配置组织；
- 采用不同于主分支的测试策略、代码结构和文档体系；
- 增加支撑可靠性、可维护性或开发体验的内部能力。

新增基础设施或依赖必须能随项目统一启动，并说明其必要性、故障边界和资源清理方式。内部自由不得改变已列出的 HTTP 状态、核心运行状态、容量限制、保留期限或用户工作流。

## 完成条件

交付必须以可复现证据证明，而不是只报告已经实现。至少验证：

1. 合法提交从 202 到成功结果的完整异步链路，以及策略拒绝不入队；
2. 幂等重复、同键冲突、非法状态转换和 retry 关系；
3. 排队取消、运行取消与成功发布之间的竞态；
4. 2 个 Worker、全局并发 4、执行者故障接管、旧执行者禁止发布和最多 3 次自动尝试；
5. 500 行、1 MiB、24 小时过期、不可用结果和幂等清理；
6. v0.1.0 SQL 绕过回归、只读身份、固定数据和双数据库隔离；
7. Web 的排队、运行、成功、失败、取消、重试、历史和结果过期主流程；
8. 干净构建、重复启动和两个独立 Compose 项目并行运行。

完成后汇报结果提交、主要设计选择、实际测试命令与结果、已知风险和未验证项。是否创建提交、推送或进入下一阶段，服从工作树届时生效的规则与用户指令。
