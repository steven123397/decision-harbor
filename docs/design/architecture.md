# 系统架构

## 范围

本文定义首轮实现的范围边界、模块划分、数据流和双数据库身份边界。需求与约束的权威来源是 [产品需求](../background/product-requirements.md) 与 [技术约束](../background/technical-constraints.md)，本文只记录实现取向的设计决策，不改写背景口径。

## 目标与非目标

首轮交付一条完整可运行的受治理 SQL 链路：用户在查询工作台提交显式 SQL，API 基于 AST 做策略判定，通过只读身份在 `analytics` 库执行，返回结果或稳定错误，并在 `platform` 库保留查询记录。整条链路可在干净 WSL 环境用统一命令启动与测试。

非目标沿用产品需求的排除项。在其之上，本轮设计额外不做：

- 异步查询队列或后台任务：查询在 HTTP 请求内同步执行（理由见关键决策）。
- 查询历史列表界面、结果导出、结果缓存。
- 多用户与鉴权：首轮无登录，所有查询视为同一匿名主体提交（背景未要求用户体系；审计按记录而非按人）。

## 模块边界

三个容器化组件：

| 组件 | 技术 | 职责 |
| --- | --- | --- |
| `web` | React 19 + Vite + TypeScript | 最小查询工作台，见 [workbench.md](workbench.md) |
| `api` | Python 3.13 + FastAPI | 策略判定、只读执行、审计记录、对外 HTTP 接口 |
| `db` | PostgreSQL 18 单容器 | 逻辑隔离的 `platform` 与 `analytics` 两库 |

API 进程内部划分为四个模块，依赖方向单向向下：

- `api`（路由层）：HTTP 端点、请求校验、响应组装；见 [query-runs-api.md](query-runs-api.md)。
- `query_runs`（记录服务）：查询记录的创建与状态更新，只写 `platform`。
- `policy`（策略）：纯函数，输入 SQL 文本，输出允许或带稳定错误码的拒绝；不触网、不触库；见 [query-governance.md](query-governance.md)。
- `executor`（执行器）：以只读身份在 `analytics` 执行已获批准的查询，实施超时与行数上限。

## 数据流

一次 `POST /api/v1/query-runs` 的处理顺序：

1. 路由层校验请求体（`sql` 为字符串且不超长），不合法直接返回 422，不产生记录。
2. `query_runs` 在 `platform` 创建记录，初始状态 `running`。
3. `policy` 判定。拒绝则更新记录为 `rejected` 并返回；允许则进入执行。
4. `executor` 通过只读连接在 `analytics` 执行，取回列定义与受上限约束的行。
5. 按结果更新记录为 `succeeded` 或 `failed`（行数、耗时、错误摘要），组装响应返回。

结果行只出现在本次 HTTP 响应中，不写入 `platform`（见关键决策）。

## 双数据库与身份边界

单一 PostgreSQL 容器承载两库、三种应用身份：

| 身份 | 权限 | 使用方 |
| --- | --- | --- |
| `platform_app` | `platform` 库属主，可建表可读写 | API 运行时（记录服务）、platform 迁移 |
| `analytics_owner` | `analytics` 库属主 | 仅 analytics 迁移与 seed，运行时不持有其凭据 |
| `analytics_reader` | 仅 `CONNECT` `analytics`、`USAGE` 契约 schema、对五张契约表 `SELECT` | 仅执行器 |

不变量：

- 用户 SQL 只能经 `analytics_reader` 连接执行；执行器不接受调用方指定连接或身份。
- API 运行时配置中不存在 `analytics_owner` 凭据，故运行时进程即使被诱导也无法写 `analytics`。
- `platform_app` 不被授予 `analytics` 的 `CONNECT`，`analytics_reader` 不被授予 `platform` 的 `CONNECT`；两库互不可达是集成测试的验证点。
- 数据库权限是应用层策略之外的独立第二道边界：策略被绕过时，写操作仍会被只读身份在数据库层拒绝。

## 关键决策

- **同步执行，不引入队列**：策略限定了超时与行数上限，单次查询耗时有界；同步模型使首轮无需任务存储、轮询协议和状态同步，链路最短、故障面最小。工作台的"执行中"状态由请求在途体现。若未来需要长查询，再引入异步（见延后决策）。
- **结果行不落库**：审计保存事实（SQL、判定、状态、行数、耗时、错误摘要），不保存数据。理由：避免把 `analytics` 业务数据复制进 `platform` 从而扩大数据暴露面，也避免审计存储随结果无界增长。代价是 `GET /api/v1/query-runs/{id}` 只能返回审计事实、不能重放结果，这与产品需求对该端点的定义一致。
- **三身份分离而非两身份**：把 analytics 的写权限单独隔离在 `analytics_owner` 并只用于迁移与 seed，使"运行时无法写分析库"由凭据不在场保证，而不只靠权限配置正确。
- **匿名单主体**：背景未定义用户体系，首轮不虚构；审计记录不含用户字段，未来加入鉴权时通过新增列迁移，不影响既有事实。

## 失败与迁移

- 进程在执行中途崩溃会留下 `running` 状态的孤儿记录。首轮接受其作为中断证据，不做自动修复或超时回收（见延后决策）。
- `db` 不可用时：`/ready` 返回失败；提交查询返回 `failed` 及稳定错误码，记录若无法写入则整个请求失败——审计写入失败时不得静默返回查询结果。
- 未来结构变更（如新增用户字段、异步执行）通过 Alembic 迁移演进 `platform`，`analytics` 契约表结构以数据契约版本为准。

## 测试接缝

- 模块依赖单向且 `policy` 为纯函数，是单元测试的主要接缝。
- 三身份的权限边界通过真实双库集成测试验证。
- 各层具体测试清单见对应专题文档；测试如何运行见 [local-runtime.md](local-runtime.md)。

## 延后决策

- 异步查询执行与任务队列：出现超出同步超时上限的合法分析需求时重议。
- `running` 孤儿记录的回收策略：出现运维困扰时重议。
- 用户体系与按人审计：产品引入鉴权需求时重议。
