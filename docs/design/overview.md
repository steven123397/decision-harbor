# 首轮总体设计

## 范围

本文覆盖首轮受治理 SQL 查询链路的总体架构：模块划分、数据流、全局不变量与跨模块关键决策。专题细节见同目录各篇：

- [查询治理设计](query-governance.md)：查询运行状态、审计事实、AST 策略与资源限制。
- [API 与查询工作台设计](api-and-workbench.md)：最小 HTTP 接口、错误语义与工作台行为。
- [数据与运行环境设计](data-and-runtime.md)：双数据库、身份边界、迁移与幂等 seed、Compose 并行隔离。
- [测试设计](testing.md)：单元、集成与浏览器测试接缝。

## 目标与非目标

产品目标与非目标以 [产品需求](../background/product-requirements.md) 为唯一权威来源，本文不重复定义。设计层面的边界：首轮只交付 Web 工作台、API、查询治理、审计、双数据库与本地 Compose 运行环境；背景非目标（LLM、自然语言转 SQL、RAG、MCP、A2A、注册与复杂 RBAC、运营后台、图表编辑器）在此不出现任何预留实现。

## 术语与场景

- 查询运行（query run）：一次用户 SQL 提交及其策略判定、执行与审计记录的完整生命周期，对应 `platform` 库中一条审计记录。
- 平台身份（platform_app）：API 访问 `platform` 库的读写身份。
- 分析只读身份（analytics_readonly）：查询执行器访问 `analytics` 库的只读身份。
- 核心场景：业务人员打开工作台 → 输入 SQL → 提交 → 看到执行中状态 → 看到结果表格或拒绝、失败原因。

## 不变量

1. 用户 SQL 只在 `analytics` 数据库以分析只读身份执行；平台写入身份永不出现在用户 SQL 的执行路径上。
2. 每个通过请求校验的提交产生且只产生一条审计记录，无论策略拒绝、执行成功或失败。
3. 数据契约（表名、字段、类型、业务口径）以 `datasets/sales-analytics-v1/contract.json` 与背景文档为准，实现不得改名、删除或重新解释；金额使用定点数，仅 `confirmed` 订单计入已实现销售额与毛利。
4. 迁移与 seed 可任意次重复执行，结果一致、无重复无残留。
5. 本地实例间完全隔离：多个工作区可同时启动同一套 Compose 配置而互不冲突。

## 模块与数据流

模块：

- `web`：React 19 + TypeScript 工作台，Vite 构建为静态资源，由 nginx 托管并将 `/api`、`/health`、`/ready` 反向代理到 `api`。
- `api`：Python 3.13 + FastAPI，内部划分 query-runs 路由、策略模块（SQLGlot）、执行器（psycopg 3）、审计仓储（SQLAlchemy 2.0）。
- `db`：PostgreSQL 18 单容器，承载 `platform` 与 `analytics` 两个逻辑数据库。
- 迁移与 seed：Alembic 双库迁移 + CSV 装载，作为启动链路中的一步运行。

提交链路数据流：

1. 浏览器加载 `web` 静态页；API 请求经 nginx 代理到 `api`。
2. `POST /api/v1/query-runs`：请求校验 → 在 `platform` 创建 `running` 状态审计记录 → 策略模块基于 SQLGlot AST 检查。
3. 策略拒绝：记录更新为 `rejected`（错误码与原因），响应返回记录。
4. 策略允许：执行器以分析只读身份在 `analytics` 执行，带语句超时与行数上限；记录更新为 `succeeded`（行数、耗时）或 `failed`（错误摘要），响应返回记录与结果（成功时）。
5. `GET /api/v1/query-runs/{id}`：从 `platform` 读取审计事实。

## 关键决策

- 同步执行模型：`POST` 请求内完成策略判定与执行并返回最终记录；记录先以 `running` 落库再转终态。"执行中"状态由客户端在等待响应期间呈现；并发请求 `GET` 同一记录时仍可观察到 `running`。理由：在满足执行中状态展示与完整审计的前提下，避免引入任务队列与后台 worker；这是首轮最简单的可运行形态。异步队列见延后决策。
- nginx 静态托管加反向代理：浏览器与 API 同源，避免 CORS 配置；对外只需一个可配置 Web 端口，API 宿主端口保留供测试与调试直连。
- 结果集不持久化：审计只保存事实（状态、行数、耗时、错误摘要），结果行仅存在于提交响应中。理由：背景只要求审计事实；持久化结果会使 `platform` 库无界增长并复制分析数据，扩大权限暴露面。
- 审计记录 id 使用应用侧生成的 UUID：无需数据库扩展，且不可枚举。

## 失败与迁移

跨模块失败路径在各专题篇展开：策略与执行失败见查询治理篇，启动与 seed 失败见数据与运行环境篇。

## 延后决策

- 异步执行队列与长时间查询的轮询模型。
- 结果集持久化与历史结果回看。
- 函数级限制（如 `pg_sleep`）：首轮由语句超时兜底，暂不引入函数黑白名单。
- 认证、用户体系与权限模型。
- 自然语言分析、语义层与 AI 辅助（背景非目标）。
